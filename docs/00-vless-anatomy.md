# 00. VLESS, разобранный по байтам

## 1. Что такое VLESS на самом деле

VLESS — это **не** протокол обфускации. Это минималистичный протокол адресации и аутентификации, у которого сознательно вырезано всё: шифрование, целостность, обфускация, антирепплей.

Единственное, что он делает:
1. предъявляет серверу UUID (аутентификация);
2. сообщает серверу, куда открыть соединение (команда + адрес + порт);
3. передаёт байты.

Всю безопасность и всю маскировку VLESS делегирует **транспорту** (TLS / REALITY / WebSocket / XHTTP). Это его сила (нулевой оверхед, нет собственного крипто-fingerprint) и его фундаментальная слабость (если транспорт палится — VLESS не спасает ничем).

Сравнение с соседями:

| | VMess | VLESS | Trojan |
|---|---|---|---|
| Собственное шифрование | да (AES-GCM/ChaCha) | нет | нет |
| Аутентификатор | HMAC(UUID, time) | UUID сырыми байтами\* | SHA224(password), hex |
| Привязка ко времени | да (±90 с, ломается при дрейфе) | нет | нет |
| Оверхед после хедера | ~40+ B на кадр | 0 | 0 |
| Устойчивость к active probing | была дырявой (replay/oracle) | своей нет — вся на транспорте | fallback на веб-сервер |

\* «сырыми байтами» = внутри TLS-туннеля, без дополнительного слоя. Для DPI это невидимо; но это **статическая 16-байтовая константа, повторяющаяся в первом кадре каждого соединения пользователя**. При компрометации ключа сессии (или при работе через доверенный CDN, который терминирует TLS) — это готовый идентификатор абонента. Важный момент для дизайна замены: см. документ 02, §6.

## 2. Формат кадра (VLESS version 0)

### Запрос клиент → сервер

```
+------+----------+---------+----------+-------+--------+-----------+---------+
| 1 B  |  16 B    |  1 B    |   M B    | 1 B   |  2 B   |    1 B    |   N B   |
+------+----------+---------+----------+-------+--------+-----------+---------+
| ver  |  UUID    | addonsL |  addons  |  cmd  |  port  | addr type |  addr   |  ...payload
+------+----------+---------+----------+-------+--------+-----------+---------+
```

* `ver` — всегда `0x00`.
* `UUID` — 16 байт, RFC 4122, сырые байты (не строка).
* `addonsL` / `addons` — protobuf-сериализованное расширение. Реально используется одно поле: `flow` (строка, например `xtls-rprx-vision`). Пусто → `addonsL = 0x00`.
* `cmd` — `0x01` TCP, `0x02` UDP, `0x03` Mux (в Mux `port`/`addr` опущены).
* `port` — big-endian uint16.
* `addr type` — `0x01` IPv4 (4 B), `0x02` domain (1 B длина + строка), `0x03` IPv6 (16 B).

### Ответ сервер → клиент

```
+------+----------+----------+
| 1 B  |   1 B    |   N B    |
+------+----------+----------+
| ver  | addonsL  |  addons  |  ...payload
+------+----------+----------+
```

Всё. Никакого «OK / ошибка»: если UUID не подошёл — соединение рвётся или уходит в fallback. Дальше голый двунаправленный поток.

### Что из этого видно снаружи

**Ничего**, пока внешний TLS цел. Но структура важна: первый исходящий кадр клиента после TLS-хендшейка имеет **сильно предсказуемую длину** — `1+16+1+1+2+1+len(addr)` плюс первый кусок payload. Для HTTPS-запроса этот payload — внутренний ClientHello. Отсюда растёт вся атака «TLS-in-TLS».

## 3. Проблема TLS-in-TLS и что такое XTLS Vision

Когда HTTPS идёт через TLS-туннель, наружу уходит:

```
[внешний TLS record]( [внутренний TLS record](реальные данные) )
```

Атака (Xue et al., «Fingerprinting Obfuscated Proxy Traffic with Encapsulated TLS Handshakes», USENIX Security 2022): первые ~10 записей туннеля имеют характерный **размерный профиль** вложенного хендшейка — ClientHello (~517 B, часто ровно 517), ServerHello+Certificate (1.4–4 KB), затем мелкие Finished. Внутри обычного HTTPS такого профиля не бывает: там сразу после хендшейка идёт запрос/ответ. Детект работает **без расшифровки**, по длинам и направлениям.

`xtls-rprx-vision` бьёт по этому двумя приёмами:

1. **Padding первых кадров.** Первые несколько записей клиента и сервера дополняются мусором, чтобы размерный профиль вложенного хендшейка растворился. Кадр Vision: `[command 1B][contentLen 2B][paddingLen 2B][content][padding]`, где `command` кодирует «продолжать padding / переключиться в direct».
2. **Direct copy (splice).** После завершения вложенного хендшейка Vision перестаёт заворачивать внутренние TLS-записи в свои и начинает **копировать их напрямую** (на Linux — через `splice(2)`, минуя userspace). С этого момента двойного шифрования нет: снаружи видны настоящие TLS-записи целевого сайта с настоящими размерами. Убирает и размерную аномалию, и оверхед CPU.

Ограничение: Vision имеет смысл только когда внутренний трафик сам TLS. Для не-TLS (QUIC, голый TCP, DNS) он деградирует в обычный padding.

## 4. REALITY: что это и почему это было гениально

REALITY — не транспорт и не шифр, а **схема установления TLS без собственного сертификата**.

Ход:

1. Клиент делает **настоящий** TLS 1.3 ClientHello с fingerprint реального браузера (uTLS: Chrome / Firefox / Safari / iOS / Edge / …), `SNI = dest` — чужой популярный домен (`www.microsoft.com`, `dl.google.com`, …), но отправляет его **на IP нашего сервера**.
2. В `session_id` (32 байта; в TLS 1.3 поле чисто декоративное) клиент прячет аутентификатор: X25519 к публичному ключу сервера, поверх — AEAD от `(shortId, timestamp)`.
3. Сервер пытается расшифровать `session_id`:
   * **не вышло** (зонд РКН/GFW или просто сканер) — сервер прозрачно проксирует TCP на настоящий `dest:443`. Зондирующий получает настоящий microsoft.com с настоящим валидным сертификатом Microsoft. Отличить нельзя;
   * **вышло** — сервер завершает хендшейк сам, подставляя перехваченный сертификат dest'а, подписанный эфемерным ключом. Клиент проверяет не цепочку, а подпись сервера известным ему ключом.
4. Дальше — обычный TLS 1.3 record layer, внутри него VLESS.

Что это дало: **иммунитет к активному зондированию** — главному оружию GFW — и отсутствие нужды в своём домене и сертификате.

Чего это **не** дало (и это ровно то, за что REALITY ловят в 2026):
* ClientHello имеет fingerprint браузера, но летит на IP, куда браузер бы не пошёл;
* браузер после захода на microsoft.com открывает десятки соединений к другим доменам — а мы открываем одно и держим часами;
* сессия длинная и симметричная, а «просмотр сайта» — короткий и download-heavy;
* dest выбирается вручную и часто совпадает у тысяч пользователей → сам dest становится маркером.

## 5. Транспорты Xray и их сигнатуры

| Транспорт | Как выглядит | Слабость |
|---|---|---|
| `tcp` + TLS/REALITY | «просто HTTPS» | TLS-in-TLS (лечится Vision); длинная симметричная сессия; один поток на соединение |
| `ws` | HTTP/1.1 Upgrade | заголовки Upgrade статичны; после апгрейда — бесконечный двунаправленный поток, чего у настоящих ws-приложений почти не бывает |
| `httpupgrade` | как ws, но без ws-фрейминга | то же, чуть меньше оверхед |
| `grpc` | HTTP/2, `POST /svc/Tun`, `content-type: application/grpc` | путь и content-type — прямая сигнатура; gRPC в открытом интернете редок, сам факт подозрителен. Вытесняется XHTTP |
| `xhttp` (ex-splithttp) | обычные HTTP/2 или HTTP/3 GET/POST | наиболее гибкий; см. ниже |
| `mkcp` | UDP со своим заголовком | собственный fingerprint, палится тривиально |

### XHTTP подробнее

XHTTP разделяет поток на два HTTP-канала:
* **download** — один долгий `GET /<path>/<session>`, сервер стримит;
* **upload** — либо один долгий `POST` (`stream-up`), либо последовательность коротких `POST /<path>/<session>/<seq>` (`packet-up`).

`packet-up` важен тем, что переживает CDN (которые не пропускают бесконечный запрос) и выглядит как обычное веб-приложение с XHR. `stream-one` (один двунаправленный HTTP/2-стрим) максимально похож на fetch-стрим и минимально оверхедный.

Параметры, влияющие на маскировку: `xPaddingBytes` (диапазон паддинга в заголовке `X-Padding`), `scMaxEachPostBytes`, `scMinPostsIntervalMs`, `scMaxBufferedPosts`, `mux`.

## 6. Итог главы

**VLESS даёт:**
* нулевой оверхед и отсутствие собственного крипто-fingerprint;
* Vision — рабочее решение TLS-in-TLS;
* REALITY — рабочее решение active probing.

**VLESS не даёт (и по дизайну не может):**
1. сокрытия **репутации IP/ASN** назначения;
2. сокрытия **формы трафика** — длительности, симметрии, cadence;
3. согласованности между заявленным TLS-fingerprint и тем, кем мы притворяемся на уровне приложения и на уровне сети;
4. защиты от **корреляции нескольких соединений** одного клиента;
5. устойчивости к whitelist-режиму («разрешено только явно разрешённое»).

Эти пять пунктов и есть то, что ловит ТСПУ в 2026 году. Разбор — в документе [01](01-threat-model-tspu.md).
