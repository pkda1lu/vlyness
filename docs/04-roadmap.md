# 04. Дорожная карта прототипа и метрики успеха

## 1. Философия: сначала дисциплина, потом крипто

Главный контринтуитивный вывод из документа 01: **бо́льшую часть современных блокировок ловит не анализ шифра, а неаккуратное поведение клиента** (пачки параллельных соединений, ретраи в цикле, ротация fingerprint под штрафом, чужой SNI). Поэтому дорожная карта начинается не с нового протокола, а с надстройки над существующим Xray.

## Этап 0 — «дисциплина поверх готового» (без единой строки нового протокола)

Проверяем гипотезу «P0 закрывает большинство срабатываний» на стоке Xray.

* VLESS + XHTTP (`stream-one`/`packet-up`) + REALITY со **своим доменом и ACME** (не чужой dest), fingerprint = один из «спокойных» (okhttp/firefox), mux включён.
* Внешняя обвязка-«супервайзер» реализует **connection budget** и **blackhole detector** из док 02 §5, §9 — управляет клиентом, ограничивая реконнекты и запрещая ротацию.
* Настоящий сайт + honest-fallback на том же домене.

Метрика этапа: время до первой заморозки и частота заморозок против ванильного VLESS+TCP+REALITY на том же канале. Если P0-дисциплина одна уже кратно улучшает — гипотеза подтверждена, и это самый дешёвый практический результат.

## Этап 1 — E2E-слой и ratchet-токен

* Реализовать §3–§6 wire-spec: Noise_IK, AEAD-кадры, ratchet-AUTH в cookie, адресный кадр.
* Транспорт `segments` поверх HTTP/2.
* Цель — снять признаки №11 (статический UUID) и №2 (рассогласование DNS/SNI/IP) и разблокировать режим A (за CDN).

## Этап 2 — Profile-движок и shaping

* Валидатор инварианта когерентности.
* Sampler длин (гистограмма + марковская цепочка), cadence-генератор, симметризатор (док 02 §8).
* Сборщик эмпирических профилей с собственного трафика.

## Этап 3 — RTC/QUIC-профиль

* HTTP/3 + WebTransport datagrams, профиль видеозвонка. Самый стойкий по форме трафика, самый дорогой в реализации.

## 2. Как измерять «неотличимость» честно

Не «на глаз». Классификаторная методология:

1. Собрать корпус: наш трафик + большой корпус трафика приложения-легенды (тот же класс).
2. Обучить набор классификаторов (по признакам из таблицы 01 §3): random forest / gradient boosting на потоковых статистиках (длины, IAT, симметрия, длительность, entropy), плюс отдельно JA3/JA4-классификатор.
3. Метрика — **ROC/AUC и, главное, FPR при фиксированном TPR цензора**. Успех = классификатор не может разделить классы лучше, чем ценой FPR, при котором цензор кладёт неприемлемую долю легитимных пользователей приложения-легенды.
4. Отдельно — **red-team активного зонда**: скрипт, повторяющий известные приёмы (probe на туннельные пути, повтор AUTH, замер timing валид/невалид, параллельные коннекты). Проверка §7 honest-fallback.

Важно: метрика **относительная** («неотличим от класса X с таким-то FPR»), а не абсолютная («неотличим от всего»). Абсолютной неотличимости не существует — см. док 02 §10.

## 3. Definition of done по каждому признаку

| Признак (01 §3) | DoD |
|---|---|
| 5 параллельных TLS | Клиент физически не открывает >`max_tls_conns`; тест-харнесс подтверждает |
| 4 ротация fp под штрафом | Fingerprint неизменен весь lifetime; blackhole detector не триггерит реконнект-шторм |
| 2 DNS↔SNI↔IP | Свой домен реально резолвится и обслуживается; зонд получает настоящий сайт |
| 11 статический UUID | Три сессии одного клиента не имеют ни одного общего байта в наблюдаемой части |
| 6 TLS-in-TLS | Размерный профиль первых 20 записей неотличим от легенды (KS-тест) |
| 7/8/9 форма | AUC классификатора формы ≤ порога; idle-туннель неотличим от idle-легенды |
| 10 probing | Red-team зонд не находит ни одного отличающего ответа/тайминга |

## 4. Этика и границы

* Инструмент двойного назначения; проектируется под задачу доступа к информации в условиях цензуры и под авторизованное исследование устойчивости сетей. Не под атаку на инфраструктуру, не под массовое злоупотребление.
* Развёртывание — на своей инфраструктуре / с явного согласия владельца.
* Никаких утверждений «гарантированно необнаружим». Все результаты формулируются как «сдвиг стоимости детекта, измеренный так-то, действительный на дату замера».

## 5. Стек прототипа (актуально)

Первоначально предполагался Go (ради переиспользования Xray-core), но на целевой машине Go не установлен, а Rust 1.98 — есть и production-viable. Решение: **ядро на Rust**. Xray-переиспользование откладывается до Этапа 1+ (интеграция роутинга) и не блокирует M1.

* Ядро (`crates/vlyness-core`) — **Rust**. Крейты: `blake2` (keyed-BLAKE2s для KDF и тегов), `chacha20poly1305` (AEAD), `snow` (Noise_IK, планируется), `subtle` (константное время), `base64`.
* Профили — JSON + валидатор инварианта когерентности.
* Тест-харнесс метрик — **Python 3.12** (scikit-learn для классификаторов, scapy/tshark для признаков) — язык независим от ядра, взаимодействие через pcap/сокеты.

Статус реализации:
* **M1 (ядро, `vlyness-core`)** — ✅ `auth`, `frame`, `address`, `noise` готовы, 33 теста, сквозной прогон стека.
* **P0 (дисциплина, `vlyness-discipline`)** — ✅ `backoff`, `budget`, `blackhole`, `ConnectionManager` готовы, 27 тестов, симуляция полного цикла заморозки ТСПУ на мок-часах.
* **Profile-движок (`vlyness-profile`)** — ✅ модель + валидатор когерентности, 17 тестов.
* **Traffic shaping (`vlyness-shaping`)** — ✅ sampler длин + cadence + симметризатор, 14 тестов.
* **Сессионный транспорт (`vlyness-transport`)** — ✅ record + session (Noise-хендшейк, seal/open) + mux, async поверх любого дуплекса, 8 тестов (loopback-интеграция клиент↔сервер).
* **Carrier: TLS + HTTP/2 (`vlyness-carrier`)** — ✅ TLS 1.3 (rustls+ring) + HTTP/2 (`h2`) `stream-one`: AUTH в cookie замкнут на Noise-prologue (§6.2, §4), honest-fallback (§7), мост AsyncRead/Write поверх h2 flow-control. 4 integration-теста на реальном TCP.
* **Закалка протокола** — ✅ анти-реплей (кэш nonce, §3), rekey исходящего ключа через управляющий кадр (§4), полный дуплекс (`Session::split` → reader/writer, общий Transport под Mutex без блокировки через await), фрагментация/сборка больших потоков (§6).
* Итого 114 тестов. **Полный стек бежит по сокету** (TCP → TLS 1.3 → HTTP/2 → cookie-auth → Noise → mux → туннель; зонд получает настоящий сайт), ядро протокола закалено (реплей/рекей/дуплекс/фрагментация).
* **Релей + бинарники (`vlyness-node`, `vlyness-cli`)** — ✅ актор-движок релея (mux-потоки ↔ реальные TCP), SOCKS5, `run_server_relay`/`TunnelClient`. Бинарники `vlyness-server`/`vlyness-client`: сервер коннектится к целям + honest-fallback; клиент валидирует Profile при старте, `ConnectionManager` (budget/backoff) управляет переподключением, локальный SOCKS5. Сквозные тесты + живой прогон процессов (python-SOCKS5 сквозь туннель = OK).
* **Cadence + blackhole в клиенте** — ✅ cadence-драйвер (idle-fill: padding-кадры при простое, §8.2); монитор трафика (`TunnelStats` up/down) + reference-пробер питают `ConnectionManager`, при вердикте Frozen туннель рвётся и соблюдается тишина (§9). Живой прогон: стабильный туннель при активном трафике/пробере без ложных заморозок.
* **Режим `segments`** — ✅ GET (нисходящий) + POST (восходящий), спариваемые по `pid` в пути (из nonce токена); honest-fallback сохранён; реплей учтён один раз на сессию. Оба режима (`stream-one`/`segments`) выбираются `VLYNESS_MODE`. Тест `tunnel_over_segments_get_post` + живой прогон.
* **ECH** — ✅ клиентский ECH через aws-lc-rs HPKE: `client_config_grease_ech` (GREASE, анти-ossification, loop-тестируется) и `client_config_ech` (настоящий ECHConfigList носителя — путь co-tenancy сквозь WL-SNI, §5.2). Выбор через `VLYNESS_ECH`/`VLYNESS_ECH_CONFIG_B64`. Тесты `grease_ech_handshake_succeeds` + `ech_config_rejects_garbage` + живой прогон segments+grease. Настоящий Enable-ECH требует ECH-фронта (CDN) — локально проверяется сборка конфига, не хендшейк.
* Итого 122 теста. **Рабочий прокси** во всех режимах: app → SOCKS5 → vlyness-client → TLS(+ECH)/HTTP2(stream|segments) → vlyness-server → реальный connect → цель, с дисциплиной, idle-fill и blackhole-детекцией.
* Осталось из масштабного: server-side ECH-термination (для полного co-tenancy без CDN — ограничено в rustls), DoH-фетч ECHConfigList из DNS HTTPS RR, packet-up вариант segments, пул/ротация профилей-носителей (док 05 §4).

* Noise Protocol Framework spec (rev 34) — обоснование §4.
* Работы по ML-детекту обфусцированного трафика (Wang, Nasr et al.) — методология §2 этого документа.
