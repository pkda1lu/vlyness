# 02. VLYNESS — дизайн

Рабочее имя: **VLYNESS** (VLESS + *lyness*, «правдоподобность»). Это не «ещё один шифр». Это **VLESS-совместимое ядро адресации, обёрнутое в движок связной легенды**.

## 0. Постановка задачи в терминах документа 01

Требование пользователя: «невозможно отличить от обычного трафика; не выдаёт реальный домен, IP и прочие паттерны».

Переформулируем честно, потому что дословная формулировка недостижима:

| Требование | Достижимо? | Как формулируется корректно |
|---|---|---|
| Не выдаёт реальный домен назначения | **Да, полностью** | Целевой домен известен только серверу; наружу виден только домен фронтенда |
| Не выдаёт реальный IP назначения | **Да, полностью** | То же |
| Неотличим от обычного трафика | **Нет как абсолют. Да как «неотличим от конкретного большого класса»** | Цель: попасть в класс, вычистить который цензор не готов из-за сопутствующего ущерба |
| Не выдаёт наличие туннеля вообще | Только при выполнении условия по IP/ASN (§3) | Наблюдатель не должен получить признак «здесь прокси» с приемлемым FPR |

Ключевая метрика проектирования — **не «энтропия трафика», а FPR цензора**: сколько легитимных пользователей он положит, если начнёт блокировать по нашему признаку. Наша задача — сделать этот FPR неприемлемо высоким.

## 1. Главный принцип: когерентность вместо обфускации

Из вывода 2 документа 01: ловят **несогласованность**. Значит центральный объект дизайна — не пакет, а **Profile** (легенда): единая декларация, из которой детерминированно выводится *всё* наблюдаемое.

```
Profile = {
  identity:   домен, сертификат, DNS-записи, реальный контент сайта
  network:    класс площадки (ASN, гео, соседство), обратный DNS
  tls:        JA3/JA4-профиль, ALPN, набор расширений, PQ key_share
  http:       версия, SETTINGS, порядок заголовков, User-Agent, cookie-политика
  traffic:    распределения длин записей, cadence, симметрия, длительность,
              сессионный график по времени суток
  fallback:   что видит любой, кто не предъявил токен
}
```

**Инвариант когерентности:** любые два наблюдаемых параметра должны быть совместимы с существованием реального приложения, описываемого Profile. Нарушение инварианта — баг такой же серьёзности, как утечка ключа.

Практическое следствие: реализация не даёт пользователю крутить ручки по отдельности. Пользователь выбирает **профиль целиком**, а не «fingerprint=chrome, path=/api, padding=100-1000». Именно ручное комбинирование несовместимых опций убивает REALITY-конфиги сегодня.

## 2. Выбор легенды: почему не «веб-сёрфинг»

Фатальная ошибка REALITY-подхода: он маскируется под **посещение сайта**, а форма трафика туннеля — как у **приложения с длинной сессией**.

| Признак | Просмотр сайта | Туннель | Видеозвонок / стрим / синхронизация |
|---|---|---|---|
| Длительность | секунды | часы | минуты–часы |
| Симметрия up/down | 1 : 20+ | ~1 : 3 | 1 : 1 … 1 : 5 |
| Сопутствующие соединения | десятки к другим доменам | нет | нет / мало |
| Idle-периоды | много | мало | мало |
| Постоянный cadence | нет | нет | **да** |

Вывод: **маскировать туннель нужно под то, чья естественная форма уже совпадает с формой туннеля.** Кандидаты (в порядке убывания устойчивости):

1. **RTC-медиа** (WebRTC/SFU: видеоконференции). Длинные симметричные сессии, постоянный cadence, толерантность к потерям, огромный сопутствующий ущерб при блокировке. Транспорт — DTLS/SRTP поверх UDP, либо TCP/TLS-fallback SFU.
2. **Синхронизация облачного хранилища / бэкап.** Длинные сессии, upload-heavy — единственный класс, где upload-тяжесть нормальна.
3. **HTTP/3-стриминг медиа с адаптивным битрейтом.** Периодические сегментные запросы, предсказуемый cadence, огромный объём в норме.
4. **Долгоживущий API-канал приложения** (push, LSP-подобные, торговые терминалы, игровые лобби).

Референс-профиль по умолчанию в этом дизайне — **(3)**, как самый простой в реализации и самый массовый; **(1)** описан как целевой профиль второй фазы.

## 3. Честная граница: IP и ASN

**Это не решается протоколом.** Если L0 режет подсеть, всё остальное неважно. Три варианта размещения, по убыванию стойкости:

| Вариант | Что видит DPI | Стойкость | Цена |
|---|---|---|---|
| **A. За общим CDN** (TLS терминирует CDN, наш бэкенд скрыт) | IP CDN, домен CDN-клиента | Высокая: блокировка бьёт по всему CDN | CDN видит открытый трафик → обязателен внутренний E2E-слой; ограничения на длинные запросы → режим `packet-up` |
| **B. Совмещённый хостинг** (наш VPS реально хостит публичный сайт с органическим трафиком) | Обычный сайт с обычной посещаемостью | Средняя: ASN всё равно «ДЦ» | Нужен настоящий сайт и настоящие посетители |
| **C. Резидентный / мобильный IP** | Домашний абонент | Высокая по L0, низкая по L1 (сервер на резидентном IP сам по себе странен) | Дорого, нестабильно |
| D. Голый VPS в популярном ДЦ | «подозрительный ASN» | **Низкая** | — |

Дизайн обязан **поддерживать A и B первым классом**, а не как костыль. Отсюда требование: транспорт должен корректно работать через промежуточный терминатор TLS, то есть **не полагаться на секретность внешнего TLS** и иметь собственный E2E-слой.

Это принципиальное расхождение с VLESS, где «нет своего шифрования» — догма. В VLYNESS свой E2E-слой **обязателен**, потому что без него режим A (единственный по-настоящему стойкий по L0) небезопасен.

## 4. Слой TLS: не подлог, а собственность

Отказываемся от REALITY-схемы «одолжить чужой сертификат». Причины:

* она даёт рассогласование DNS ↔ SNI ↔ IP (сигнал №2 из таблицы 01 §3) — DPI видит TLS к microsoft.com на IP, который не Microsoft, при том что абонент не резолвил microsoft.com;
* она принуждает к uTLS-имитации, а имитация всегда отстаёт от оригинала (пример: PQ key_share);
* dest'ы централизуются: тысячи пользователей на 20 популярных dest — сам dest становится маркером.

Вместо этого: **свой домен, свой ACME-сертификат, честный DNS, честный сайт.** Стойкость к активному зондированию обеспечивается не подлогом, а тем, что **сервер действительно является этим сайтом** (см. §7).

### Fingerprint-политика

* Клиент не имитирует браузер. Клиент имитирует **приложение**, соответствующее Profile: мобильный/десктопный медиа-клиент. У таких клиентов JA3 — это JA3 их HTTP-библиотеки (OkHttp, Cronet, NSURLSession, реже Go/Rust-стеки). Такие профили массовы и разнообразны, и — по наблюдениям июня 2026 — не входят в приоритетные цели.
* **Fingerprint фиксируется при установке и никогда не меняется** (штраф 600 с за ротацию, док 01 §2 L3).
* Профиль генерируется из **одного описания** вместе с User-Agent, HTTP/2 SETTINGS и ALPN, чтобы исключить рассогласование между слоями. Отдельной ручки «fingerprint» в конфиге нет.
* PQ key_share включается/выключается вместе с профилем, а не отдельно.

## 5. Транспортный слой: HTTP как несущая

Несущая — **HTTP/2 или HTTP/3 поверх настоящего TLS**, стилизованный под медиа-клиент из Profile.

Три режима, выбираются профилем и средой:

| Режим | Форма | Где применим |
|---|---|---|
| `stream` | один двунаправленный HTTP/2-стрим (`POST` с бесконечным телом) | прямое подключение, режим B |
| `segments` | `GET` сегментов + `POST` телеметрии, оба короткие и периодические | за CDN (режим A), максимальное правдоподобие для медиа-профиля |
| `datagram` | HTTP/3 + WebTransport/QUIC datagrams | RTC-профиль, фаза 2 |

Режим `segments` — сердце маскировки медиа-профиля. Клиент запрашивает «сегменты» с растущим индексом, как ABR-плеер:

```
GET  /v1/media/{sessionId}/seg/{n}.m4s     ← нисходящий поток (данные туннеля)
POST /v1/media/{sessionId}/telemetry       ← восходящий поток (данные туннеля)
```

Сегментные запросы естественно короткие (2–10 с), что решает признак «длительность сессии»: TLS-соединение переиспользуется, но **HTTP-запросы имеют нормальное распределение длительности**, а сама сессия выглядит как «пользователь смотрит длинное видео» — что нормально и массово.

### Мультиплексирование обязательно

Из док 01 §2 L3: >3 параллельных TLS к одному SNI = заморозка. Поэтому:

* **одно TLS-соединение на профиль**, все пользовательские потоки мультиплексируются внутри (в HTTP/2 — по одному стриму на поток либо собственный mux внутри одного стрима);
* **connection budget manager**: жёсткий потолок одновременных TLS-соединений (по умолчанию 1, максимум 2 при переключении), минимальный интервал между установлениями (по умолчанию ≥ 800 мс, с джиттером), запрет «bursty reconnect»;
* при разрыве — экспоненциальный backoff с полным джиттером, база 2 с, потолок 300 с, **без смены fingerprint и без смены SNI**.

## 6. Слой сессии: что заменяет VLESS-хедер

Ядро адресации переиспользуем из VLESS (оно хорошее), но чиним три вещи.

### 6.1. Ratcheting identity вместо статического UUID

VLESS шлёт 16 постоянных байт в первом кадре. Заменяем на производный идентификатор:

```
epoch   = floor(unixtime / 3600)
salt    = 32 случайных байта (генерируются клиентом на сессию)
authKey = HKDF(psk, salt, "vlyness/auth/v1" || epoch)
authTag = HMAC(authKey, sessionId || clientNonce)[0..16]
```

Свойства: наружу уходит только `(salt, clientNonce, authTag)` — все три выглядят как случайные, ни один не повторяется между сессиями. Сервер проверяет `epoch ∈ {now-1, now, now+1}` (устойчивость к дрейфу часов до часа — в отличие от VMess с его ±90 с). Реплей ловится кэшем `clientNonce` в пределах окна.

### 6.2. Токен предъявляется в HTTP, а не в теле

Токен уходит в **cookie фиксированной длины**, соответствующей Profile:

```
Cookie: sid=<base64url(salt || clientNonce || authTag)>; pref=<константа профиля>
```

Длина строки константна для всех пользователей и всех сессий — иначе длина cookie сама становится каналом. Значение неотличимо от base64 обычного идентификатора сессии.

Ни в коем случае **не в пути URL**: путь логируется CDN и веб-сервером и становится статической сигнатурой (болезнь gRPC-транспорта с его `/svc/Tun`).

### 6.3. Внутренний E2E-слой (обязателен)

Поверх HTTP-несущей — собственный AEAD-канал, чтобы режим A (за CDN) был безопасен:

* Noise-подобный хендшейк `IK` (клиент знает статический ключ сервера), 0-RTT для данных при известном ключе.
* ChaCha20-Poly1305 или AES-GCM (по AES-NI), rekey каждые 2^20 кадров.
* Кадр: `[type 1B][length 2B][padding_len 2B][payload][padding]`, где `length`/`padding_len` — уже внутри AEAD, наружу не видны.
* Внутри — VLESS-совместимая адресация (`cmd`/`port`/`addr type`/`addr`) без версии и UUID: они больше не нужны.

Итоговая длина оверхеда на кадр: 5 байт заголовка + 16 байт тега. Больше, чем VLESS (0), но это плата за режим A.

## 7. Anti-probing: сервер, который действительно является сайтом

REALITY решает probing подлогом. Мы решаем **правдой**:

1. На домене работает **настоящий сайт с настоящим контентом**, соответствующий Profile (медиа-каталог для медиа-профиля). Он отдаёт нормальные страницы, нормальный `robots.txt`, нормальные заголовки, реально индексируется.
2. Эндпоинты туннеля **существуют для всех** и ведут себя как настоящее API: без токена — валидная сессия «демо-контента», отдающая настоящие медиа-сегменты из статики. Не 404, не 403, не разрыв: **успешный ответ**. Зонд, пришедший на `/v1/media/.../seg/1.m4s`, получает медиа-файл.
3. **Timing-safe проверка токена** и одинаковая по времени обработка валидного и невалидного случая (в т.ч. одинаковые задержки обращения к бэкенду). Разница во времени ответа — классический канал детекта.
4. Никаких признаков в заголовках ответа: `server`, `date`, порядок заголовков, `alt-svc` — как у веб-сервера из Profile, для всех клиентов одинаково.
5. Сервер **не различает** зонд и абонента на уровне TCP/TLS вообще: решение принимается только после разбора HTTP-запроса, к этому моменту наблюдателю уже нечего измерять.

Дополнительно: запрет на «умный» бан сканеров. Любая реакция, отличающая нас от обычного сайта (бан по IP, tarpit, отличающийся ответ на повторный запрос) — это канал детекта.

## 8. Traffic shaping: форма важнее содержания

Три подсистемы.

### 8.1. Sampler длин

Не uniform random padding — он **сам по себе аномалия** (реальный HTTPS даёт бимодальное распределение с пиком на MSS и пиком на мелких записях). Вместо этого:

* профиль несёт **эмпирическое распределение длин записей**, снятое с реального приложения-легенды (гистограмма + марковская цепочка переходов между «крупная / средняя / мелкая»);
* каждая исходящая запись дополняется/дробится так, чтобы длина была сэмплом из этого распределения;
* распределение — часть Profile и обновляется вместе с ним.

### 8.2. Cadence-генератор

Медиа-профиль подразумевает **постоянный ритм** запросов. Значит:

* сегментные запросы идут по расписанию профиля (например, каждые 4 с ± джиттер), **независимо от того, есть ли пользовательские данные**;
* при отсутствии данных — сегмент заполняется padding'ом до нормального размера. Idle-туннель выглядит как воспроизведение видео;
* при избытке данных — используется механизм «повышения битрейта» ABR (запрос сегментов более высокого качества), что даёт естественный способ легально масштабировать пропускную способность.

Цена: постоянный фоновый трафик даже в простое. Это плата за устранение признаков «on/off по запросам пользователя» и «длинные idle». Профиль должен позволять выбирать между экономией и стойкостью явно.

### 8.3. Симметризатор

Целевое соотношение up/down берётся из профиля (для медиа ~1:15). Восходящий канал (`telemetry`) дросселируется и дополняется, чтобы не выбиваться. Это ограничивает реальную скорость upload — честный компромисс, который надо озвучивать пользователю, а не прятать.

## 9. Клиентская дисциплина: не усугублять

Отдельная подсистема, которой нет ни в одном существующем клиенте, и которая по док 01 §4 (вывод 3) даёт больше, чем любой шифр.

**Blackhole detector.** Отличает «сеть упала» от «нас заморозили»:
* признак заморозки — исходящие уходят, входящих ноль, при этом **другие хосты доступны**;
* при обнаружении: не ретраить в цикле, не менять fingerprint, не менять SNI. Уйти в тишину минимум на 150 с (больше наблюдаемого окна 120 с), затем один пробный коннект;
* при повторе — 600+ с, затем переключение на **другой профиль целиком** (другой домен, другая площадка, другой fingerprint), но не раньше.

**Профильные окна активности.** Сессии в 4 утра длиной 6 часов — аномалия для медиа-профиля. Профиль несёт суточный график, и клиент по умолчанию не поддерживает вечный туннель, а переустанавливает сессии по расписанию, соответствующему легенде.

## 10. Что этот дизайн НЕ решает

Прямо и без маркетинга:

1. **Репутация ASN/подсети.** Единственная защита — размещение (§3). Протокол бессилен.
2. **Whitelist-режим — вынесен в отдельный первоклассный сценарий, см. [док 05](05-whitelist-traversal.md).** Кратко: проходится, но только *внутри* разрешённого носителя (co-tenancy на разрешённом CDN + ECH, либо разрешённый сервис как канал). Протокол не создаёт носитель из ничего — его надо иметь и вовремя менять; это операционная задача, которую дизайн поддерживает (пул профилей, маяк-канал), но не отменяет.
3. **Глобальный пассивный наблюдатель с корреляцией по времени.** Тайминг-корреляция входа и выхода не побеждается ничем, кроме постоянного cover traffic и задержек, несовместимых с интерактивным использованием.
4. **Компрометация сервера.** Сервер видит всё в открытом виде — это прокси, а не Tor. Модель доверия: пользователь доверяет владельцу сервера.
5. **Масштаб.** Дизайн предполагает малые приватные развёртывания. Публичный сервис с тысячами абонентов на одном домене ловится по кросс-абонентской корреляции независимо от качества протокола.
6. **Гарантий «навсегда» нет.** Всё описанное — сдвиг стоимости детекта, а не доказательство невозможности. Профили — расходный материал и должны обновляться.

Оценка «стойкость / трудозатраты» по признакам из таблицы 01 §3:

| Приоритет | Компонент | Закрывает признаки |
|---|---|---|
| **P0** | connection budget manager + mux | 5 (самый частый триггер сегодня) |
| **P0** | blackhole detector + backoff без ротации | 4 |
| **P0** | свой домен + ACME + настоящий сайт + honest-fallback | 2, 10 |
| **P1** | HTTP-несущая `segments` + ratchet-токен в cookie | 8, 11 |
| **P1** | E2E-слой (для режима A за CDN) | 1 (косвенно, разблокирует лучшую площадку) |
| **P2** | Profile-движок с инвариантом когерентности | 3 |
| **P2** | sampler длин + cadence + симметризатор | 6, 7, 9 |
| **P3** | RTC/QUIC-профиль | усиление 7, 9 |

Заметьте: **P0 не требует нового протокола вообще** — это дисциплина подключения и правильная площадка. Это и есть главный практический вывод: сегодня большинство блокировок ловят не криптографию, а неаккуратное поведение клиента.
